# Проверка качества кода

Определи область проверки по запросу пользователя: Python, frontend,
документация или весь проект. Соблюдай корневой [AGENTS.md](../../../AGENTS.md).
Команды ниже выполняются из корня репозитория при установленных зависимостях.
Установка описана в [README.md](../../../README.md); не используй npx для
неявного скачивания отсутствующего инструмента.

Сначала запусти относящиеся к запросу проверки без изменения файлов:

```powershell
python -m ruff check backend/app import-obsidian.py
python -m ruff format --check backend/app import-obsidian.py
npm --prefix frontend run lint
npm --prefix frontend run format:check
npm --prefix frontend run build
```

Для отдельного Python-файла передай его путь вместо обоих путей.
Для отдельного frontend-файла из каталога frontend используй локальный
`npm exec --no -- eslint src/main.jsx --max-warnings 0` или
`npm exec --no -- prettier --check src/main.jsx --ignore-path ../.prettierignore`.
Для документации достаточно соответствующей проверки Prettier.
Сборка Vite создаёт frontend/dist, но не меняет исходники; при изменении
frontend перед завершением выполни её даже после адресных проверок.

Источники правил (не дублируй их в скилле):

- [pyproject.toml](../../../pyproject.toml) — Ruff lint и форматирование Python.
- [frontend/eslint.config.mjs](../../../frontend/eslint.config.mjs) — JS/JSX и Hooks.
- [.prettierrc.json](../../../.prettierrc.json) и
  [.prettierignore](../../../.prettierignore) — форматирование и исключения.
- [frontend/package.json](../../../frontend/package.json) — npm-команды.

При запросе только диагностики ничего не исправляй. Зафиксируй исходные ошибки,
коды завершения и недоступные проверки. Не запускай Python-приложение или импортёр
ради статического анализа: они создают каталоги и могут менять данные.

При запросе исправлений вноси минимальные изменения в согласованной области.
Для Python используй `python -m ruff check --fix <пути>` и отдельно
`python -m ruff format <пути>`. Для всего frontend существуют `lint:fix`
и `format:write`; при локальной задаче используй адресные вызовы локальных
ESLint (`--fix --fix-type problem,suggestion`) и Prettier (`--write`).
Не применяй `--unsafe-fixes` автоматически. Изменение зависимостей эффектов
React требует анализа поведения, а не механического добавления переменных.

Не отключай правила и не меняй поведение приложения только ради зелёной проверки.
Проверь diff, затем повтори относящиеся к изменениям проверки, включая сборку
frontend. В конце сообщи, что прошло, что не прошло, какие проблемы существовали
до изменений и что осталось. Если команда не выполнена, укажи причину.
